# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A personal collection of Claude Code **skills**, scoped to this project only. Skills live in [.claude/skills/](.claude/skills/) so they're auto-loaded when Claude Code is launched from this directory (or any subdirectory) and are **not** available globally. There is no application to build, deploy, or test — the artifacts here are the skills themselves.

Each subdirectory of `.claude/skills/` is one skill, identified by a `SKILL.md` with YAML frontmatter (`name`, `description`). The `description` field is what Claude reads to decide whether to invoke a skill, so it must enumerate the trigger phrases / user intents that should activate it.

## Skills currently in this repo

- [weekly-meal-plan](.claude/skills/weekly-meal-plan/SKILL.md) — generates a Mon→Sun triathlon meal plan from TrainingPeaks data, renders to PDF, uploads to Google Drive, and answers follow-up questions during the week. Owns its own state under `plans/` (one markdown file per week, which doubles as the cache). The plan-file schema and the recipe-image provider chain live in `reference/`, read on demand during plan creation only.
- [desmor-pool-schedule](.claude/skills/desmor-pool-schedule/SKILL.md) — looks up open-swim hours for the Desmor pool in Rio Maior, with a one-week cache in `cache/current.json` and a Gmail recheck for mid-week schedule corrections.
- [update-dependencies](.claude/skills/update-dependencies/SKILL.md) — pulls latest commits for vendored submodules (currently `trainingpeaks-mcp`) and re-runs the install only when `pyproject.toml`/lock/entry-points changed. Skips reinstall for source-only changes since the editable install picks them up live. Reminds the user to restart Claude Code so the running MCP server process gets replaced.
- [bootstrap](.claude/skills/bootstrap/SKILL.md) — sets up a freshly cloned working copy: `git submodule update --init`, then installs each submodule's deps (currently just `trainingpeaks-mcp` into `trainingpeaks-mcp/.venv/` with the `[browser]` extra). Hands `tp-mcp auth` off to the user since it's interactive and touches the system keyring. Defers to the submodule's own README for canonical install steps.
- [llm-wiki](.claude/skills/llm-wiki/SKILL.md) — creates and maintains an LLM-wiki for a *target* project: a knowledge base of durable facts (decisions, invariants, domain vocabulary, module boundaries, gotchas) stored as an [Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing/) v0.1 bundle at `<project>/wiki/`. Unlike the other skills here it operates on other repos, not this one. Ships [scripts/okf.py](.claude/skills/llm-wiki/scripts/okf.py) (lint / stale / index) and a condensed offline copy of the spec under `reference/`.

## External dependencies these skills assume

The skills shell out to tools/services that must be present on the host. Most are the user's environment, except `trainingpeaks-mcp` which is now vendored as a submodule:

- **TrainingPeaks MCP** (`mcp__trainingpeaks__tp_*`) — vendored at [trainingpeaks-mcp/](trainingpeaks-mcp) as a git submodule from `https://github.com/JamsusMaximus/trainingpeaks-mcp.git` and registered at project scope in [.mcp.json](.mcp.json), so it loads only when Claude Code is launched from this directory. After cloning this repo, run `git submodule update --init`, then `python3 -m venv trainingpeaks-mcp/.venv && trainingpeaks-mcp/.venv/bin/pip install -e "trainingpeaks-mcp[browser]"`, then `trainingpeaks-mcp/.venv/bin/tp-mcp auth` to store the TrainingPeaks cookie in the system keyring. Used by `weekly-meal-plan` to pull planned workouts, fitness (CTL/ATL/TSB), and the focus/next event.
- **Gmail MCP** (`mcp__claude_ai_Gmail__*`) — `desmor-pool-schedule` uses it to scan for mid-week correction emails from `secretaria.piscinas@desmor.pt`.
- **Local image generation** (Apple Silicon only) — the **default** provider for `weekly-meal-plan` action A6.5, so recipe photos need no API key, no quota and no network. [scripts/gen-recipe-images.py](.claude/skills/weekly-meal-plan/scripts/gen-recipe-images.py) drives [mflux](https://github.com/filipstrand/mflux) (a native MLX port) running **Z-Image Turbo** — `mflux-community/z-image-turbo-mflux-q8`, 6B params, Apache-2.0, ungated, ~11 GB fetched once into `~/.cache/huggingface`. Its Python deps live in their own venv at [scripts/.venv-imagegen/](.claude/skills/weekly-meal-plan/scripts), pinned in [scripts/requirements-imagegen.txt](.claude/skills/weekly-meal-plan/scripts/requirements-imagegen.txt) and gitignored — kept **separate** from the renderer's `scripts/.venv/` because mflux drags in mlx + torch + transformers (~1.2 GB) that a markdown→PDF conversion has no business carrying. Build it with an explicit ≥3.10 interpreter (`/opt/homebrew/bin/python3.14`): macOS's system `python3` is 3.9.6 and mflux rejects it. ~40 s/image on an M5 Pro, ~13 min for a 20-recipe week.
- **Composio Gemini** (`COMPOSIO_MULTI_EXECUTE_TOOL` → `GEMINI_GENERATE_IMAGE`, `gemini-2.5-flash-image`) — first *hosted* fallback for A6.5, used when the local generator can't run (non-Apple-Silicon host, model won't load). Skipping images entirely is also acceptable; the renderer falls back to emoji banners.
- **`chromium`** (system binary) — required by [scripts/md-to-pdf.py](.claude/skills/weekly-meal-plan/scripts/md-to-pdf.py) for headless PDF rendering. On Arch: `pacman -S chromium`. The script's Python dependency (`markdown`) is **not** a system dependency: it lives in a dedicated venv at [scripts/.venv/](.claude/skills/weekly-meal-plan/scripts), pinned in [scripts/requirements.txt](.claude/skills/weekly-meal-plan/scripts/requirements.txt), and the renderer is invoked via `scripts/.venv/bin/python` (the `.venv/` is gitignored; SKILL.md action A7 creates it on first run from requirements.txt). Do not `pip install --user markdown` — use the venv.
- **`rclone`** with a pre-configured `gdrive:` remote pointing at the user's Google Drive — used to upload the rendered PDF to the `Meal Plans/` folder. The Google Drive MCP cannot handle a ~1 MB PDF in a single inline-base64 tool call, so `rclone` is the only supported path.
- **`magick`** (ImageMagick) — resizes the *hosted* providers' 1248×832 PNGs to 800×533 JPEG q85 before they're embedded in the PDF. Not needed on the default local path, which resizes in-process with Pillow.
- **`git`** (system binary) — `llm-wiki`'s [scripts/okf.py](.claude/skills/llm-wiki/scripts/okf.py) shells out to `git ls-files` / `diff` / `merge-base` in the *target* repo to derive staleness and coverage. Its Python deps (`PyYAML`, `pathspec`) live in a dedicated venv at [scripts/.venv/](.claude/skills/llm-wiki/scripts), pinned in [scripts/requirements.txt](.claude/skills/llm-wiki/scripts/requirements.txt), created on first run and gitignored — same convention as `weekly-meal-plan`.

## Editing a skill

1. Edit the relevant `SKILL.md` (or scripts under it).
2. The skill is reloaded the next time Claude Code starts in this directory. No build step.
3. The `description:` frontmatter field is the *only* thing that controls when Claude reaches for the skill — if you change behavior, make sure the description still matches the trigger phrases you want.

## Conventions specific to `weekly-meal-plan`

The PDF renderer is **not** a generic markdown-to-HTML converter — `parse_plan()` in [md-to-pdf.py](.claude/skills/weekly-meal-plan/scripts/md-to-pdf.py) parses the schema documented in [reference/plan-schema.md](.claude/skills/weekly-meal-plan/reference/plan-schema.md) directly (`## Training Overview`, `## Meal Plan`, `### {Day} — {Session}`, `## Shopping List` with `### {Category}`, `## Recipes` with `### {Day}` and `#### {Dish}` plus the `**Tags:**` / `**Per serving:**` / `**Time:**` metadata block). Changing those headings or bullet shapes will silently drop content from the PDF. If you adjust the schema in `reference/plan-schema.md`, update the parser to match.

Recipe images are looked up by slug (`slugify(dish_title)` — NFKD normalize, strip accents, lowercase, non-alphanumerics → `-`) at `plans/images/{week-stem-minus-meal-plan-prefix}/{slug}.{jpg|jpeg|png|webp}`. The same slug function must be used when saving generated images. [gen-recipe-images.py](.claude/skills/weekly-meal-plan/scripts/gen-recipe-images.py) carries a **second copy** of `slugify` for exactly this reason — the two must stay byte-for-byte identical, since drift doesn't error, it just writes files the renderer never looks for and quietly downgrades every affected recipe to an emoji banner.

## Conventions specific to `desmor-pool-schedule`

`cache/current.json` always reflects the **original** PDF in `pools[*].schedule`; mid-week corrections live in `date_overrides[date][pool]` as a *full replacement list of slots*, not a diff. This separation means the override logic can be re-derived if it changes. The merged view (override wins per-day) is computed at read time, not persisted.

## Conventions specific to `llm-wiki`

This skill is **the one skill here that is global and targets other repos**. It must fire when the user starts a new project, which by definition is not this repo, so it is symlinked: `~/.claude/skills/llm-wiki` → `.claude/skills/llm-wiki` in this repo. The repo stays the source of truth; edits take effect everywhere with no copy step. If the symlink is missing after a fresh clone, recreate it with `ln -s "$PWD/.claude/skills/llm-wiki" ~/.claude/skills/llm-wiki`.

Because it runs with `$PWD` set to the *target* project, `okf.py` must always be invoked by absolute path (`~/.claude/skills/llm-wiki/scripts/...`), never by a path relative to the skill directory. `--bundle` resolves against `$PWD`; `--repo` defaults to the bundle's git root.

Wiki staleness rests entirely on two **producer-extension** frontmatter keys that OKF itself does not define: `sources` (gitignore-syntax globs, matched against `git ls-files` in the target repo) and `source_commit` (the commit at which those sources were last actually read). `okf.py stale` diffs one against the other. A concept with no `sources` is timeless and never reported stale — that is intentional, and the skill's half-life rule pushes authors toward such pages. Adding `sources` to a page whose truth doesn't depend on that code manufactures false staleness.

Coverage (`S004`) is computed over `git ls-files`, i.e. **tracked files only**. That means the target project's `.gitignore` is already honoured transitively, and `DEFAULT_IGNORE` deliberately contains no `node_modules`/`dist`/`.venv` patterns — those can never reach the script. Do not "fix" this by merging `.gitignore` into the ignore set: git's rule is *tracked beats ignored*, so a file committed before being gitignored stays tracked, and suppressing it would silently shrink the coverage report. A submodule appears as a single gitlink entry at its bare path, so `normalize_sources` skips the usual `dir/**` expansion for it — that is what lets a page pin `sources: [trainingpeaks-mcp]` and get an `S001` when the pointer is bumped.

`okf.py` encodes OKF v0.1 §6/§7/§9 directly: `index.md` and `log.md` are reserved filenames, only the **root** `index.md` may carry frontmatter (it declares `okf_version`), and `type` is the sole required field. `index --write` regenerates every index from concept frontmatter, so a hand-curated index needs the `<!-- okf:manual -->` marker to survive. If you change the bundle layout in SKILL.md, update the checks in `okf.py` to match — same coupling as `weekly-meal-plan`'s `parse_plan()`.
